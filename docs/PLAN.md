# Collection Tag Sync — Lightweight Development Plan

## 1. Process intent

Use the useful parts of an ADR- and TDD-driven workflow without turning a small Jellyfin plugin into a heavyweight program.

Core rules:

- ADR meaning is aligned before production coding.
- Behavioral work begins with a failing test.
- Issues describe user-visible behavior, not individual classes.
- Each implementation slice stays focused and produces clear acceptance evidence.
- Architectural contradictions return to design discussion.
- UI work follows stable server-side semantics.

---

## 2. Phase 0 — ADR alignment gate

**No production synchronization code begins in this phase.**

For ADR-001 through ADR-007:

1. Read the decision and consequences.
2. Walk through at least one addition, removal, manual-state, and cascade example where applicable.
3. Confirm failure and disable behavior.
4. Record any rejected alternatives worth retaining.
5. Revise ambiguous language.
6. Mark the ADR **Accepted**.

Exit criteria:

- All behaviorally significant ADRs are Accepted.
- `DESIGN.md` and ADRs do not contradict each other.
- Additive and Authoritative examples are understood.
- External metadata changes and Authoritative cascade safety are understood.
- Run-once as the V1 manual-only workflow is understood.
- DAG rejection and run-once behavior are understood.

---

## 3. Phase 1 — Repository skeleton and integration spike

Create:

- solution and plugin project from the Jellyfin plugin template;
- test project;
- base plugin configuration;
- CI restore/build/test workflow;
- local Jellyfin test-server instructions;
- `build.yaml` with placeholder version and a permanent plugin GUID.

Perform a bounded Jellyfin spike against the selected target ABI:

1. Load the minimal plugin.
2. Subscribe to collection add/remove events.
3. Subscribe to general item-update events.
4. Add/remove a direct tag and confirm persistence across restart.
5. Confirm case-equivalent tag add, read, filter, and removal behavior against
   the source-researched 10.11.x contract.
6. Add/remove Movie and Series collection membership.
7. Observe events generated by plugin writes.
8. Verify collection creation behavior, duplicate-name handling, and persistence
   after the surrounding workflow is canceled or fails.
9. Build a JPRM ZIP and install it manually.
10. Load it from a temporary custom manifest.

Spike output:

- compatibility notes;
- chosen .NET target;
- exact Jellyfin package versions;
- confirmed APIs and event behavior;
- a small set of contract/integration tests where feasible.

Throw away exploratory code that does not meet production test standards.

Exit criteria:

```text
dotnet build
dotnet test
```

pass from a clean checkout, and a minimal packaged plugin loads on the target Jellyfin server.

## 4. Phase 2 — Pure graph and planning engine, test first

Implement through tests:

1. Tag normalization and node identity.
2. Collection GUID identity.
3. Target-group validation.
4. One-target-group-per-target enforcement.
5. Group flattening into graph edges.
6. Direct self-cycle rejection.
7. Multi-hop cycle rejection.
8. Human-readable cycle path.
9. Topological ordering.
10. Observed/effective state evaluation.
11. Additive planning.
12. Authoritative planning.
13. Many-source OR aggregation.
14. Multi-hop final-state propagation.
15. Deterministic delta generation.
16. Idempotence.

This phase should not reference live Jellyfin objects.

Exit criteria:

- Pure planner covers all formal semantics in `DESIGN.md`.
- Applying a plan and replanning returns an empty plan.
- Property/high-value invariant tests pass.

## 5. Phase 3 — First walking vertical slice

Implement one end-to-end path:

```text
Hardcoded Tag → Collection Additive mapping
        ↓
Jellyfin ItemUpdated event
        ↓
dirty-item set
        ↓
planner
        ↓
collection writer
        ↓
self-generated collection event
        ↓
second pass with zero delta
```

Purpose:

- validate the architecture before completing every feature;
- prove event, queue, planner, writer, and self-event settling work together;
- expose Jellyfin API assumptions early.

Exit criteria:

- One Movie and one Series can synchronize end-to-end.
- Duplicate/self-events do not cause repeated writes.
- Integration tests or reproducible manual evidence exist.

## 6. Phase 4 — Complete continuous synchronization

Add behavior slices for:

- Collection → Tag;
- Authoritative additions/removals;
- many sources to one target;
- one source to several target groups;
- multi-hop DAG propagation;
- configuration validation and enqueued background reconcile;
- fail-closed unresolved-group behavior and persistent missing-collection
  diagnostics;
- deduplicating dirty set;
- one serialized coordinator;
- event-storm/scan fallback;
- failed-item quarantine until Full Reconcile.

Exit criteria:

- All continuous V1 behavior is implemented server-side.
- No UI-specific logic is required to enforce correctness.

---

## 7. Phase 5 — Full Reconcile and recovery

Implement the Jellyfin scheduled task using the same planner and writer.

Test:

- missed addition repair;
- unsupported Authoritative target removal;
- partial plan repair;
- plugin downtime drift;
- delayed startup reconciliation and pending-request coalescing;
- startup delay defaults, boundaries, and active-scan deferral;
- continuation after one item failure;
- event-storm Full Reconcile flag;
- manual invocation;
- destructive circuit-breaker pause with zero applied mutations;
- absolute, percentage, population-floor, and exact-boundary behavior;
- confirmed execution of a recomputed paused plan.

Exit criteria:

- Full Reconcile is the reliable recovery path for every supported drift case.

## 8. Phase 6 — Preview and run-once

Implement:

- preview request/response;
- item-level additions and removals;
- downstream cascade simulation;
- final settled-state output;
- Additive run-once;
- Authoritative run-once;
- staged reverse/bootstrap run-once;
- enabled continuous-target conflict rejection;
- per-item run-once exclusions with downstream recomputation;
- existing collection target selection;
- picker-only existing collection selection;
- add-new collection workflow returning the selected GUID;
- duplicate-name rejection and existing-match picker recovery;
- created-collection persistence after surrounding workflow cancellation or
  save failure;
- destructive confirmation and stale-preview handling;
- candidate-before-persist configuration activation;
- removal-set change rejection with no configuration save;
- preview-authorization expiry, binding, single-use, and restart behavior;
- save response revision and background reconciliation status contract.

Exit criteria:

- Preview and execution use the same planner semantics.
- A tag-based collection bootstrap works without creating a persistent mapping.

## 9. Phase 7 — Configuration UI

Build a thin UI over validated server APIs:

- group list by target;
- tag and collection node selectors;
- collection picker;
- create-new-collection option;
- source list editor;
- Additive/Authoritative explanation;
- enable/disable;
- cycle diagnostics;
- destructive preview/confirmation;
- run-once page;
- configuration-triggered reconciliation status;
- Full Reconcile controls and status.

Do not duplicate graph or policy logic in JavaScript.

Exit criteria:

- All configuration actions remain server-validated.
- A user can configure the motivating Kid Approved flow without manually editing JSON/XML.

## 11. Lightweight issue format

Each implementation issue should contain:

```markdown
## Behavior
What user-visible or architectural behavior is being added?

## Examples
Concrete positive, negative, removal, and edge examples.

## ADRs
Relevant accepted ADR numbers.

## Acceptance tests
Observable tests that prove completion.

## Out of scope
Related behavior intentionally excluded.
```

Issue sizing guidance:

- One behavior slice, not one file/class.
- Prefer vertical slices after the pure engine exists.
- Avoid an omnibus issue for all synchronization.
- Avoid dozens of administrative micro-tickets.

---

## 12. Commit and review standard

For each behavior slice:

1. Add a failing test.
2. Confirm the intended failure.
3. Implement the minimum behavior.
4. Run targeted tests.
5. Refactor.
6. Run the full suite.
7. Commit one focused change.
8. Record acceptance evidence in the issue/PR.

Review should check two axes:

- **Behavioral:** Does the implementation match the accepted ADRs and examples?
- **Engineering:** Is the code maintainable, testable, secure, and compatible with Jellyfin plugin constraints?
